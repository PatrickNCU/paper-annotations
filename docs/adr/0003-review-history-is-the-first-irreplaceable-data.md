# 複習歷史是第一份不可重生的資料，因此存成追加式紀錄、由重放算出排程

到 1.4.0 為止，這套工具的每一個產物都可以從卡片、畫記、要點加上原文重建出來，逐位元組相同。這條性質撐起了整個架構：`annotated/` 可以刪掉重建，複習頁可以隨時重生，錯了就重跑。

間隔重複打破它。「我哪一天複習過這張卡、當時答得如何」推導不出來——它是使用者按下按鈕的那一刻才存在的事實，弄丟就是弄丟了。這是系統裡第一份具有這種性質的資料，所以它的儲存方式不能沿用其他產物的做法。

我們決定：**每張卡一個追加式的純文字紀錄檔，排程狀態不儲存、每次由重放紀錄算出來。**

```
notes/reviews/0001.md
---
card: "0001"
---
2026-08-17 good
2026-08-24 again
2026-08-25 hard
```

## Considered Options

- **把排程狀態寫進卡片的 frontmatter**（`due: 2026-09-01`、`ease: 2.5`）：最少檔案，複習時只要讀卡。但卡片是使用者手寫、agent 改寫、`reanchor.py` 重寫的檔案——每一次改寫都變成一次可能弄丟排程的機會，而弄丟是不可逆的。把不可重生的資料放進最常被程式覆寫的檔案裡，是這幾個選項中最危險的一個。
- **單一 log 檔**（`notes/reviews/log.jsonl`）：歷史完整、寫入簡單。但登記簿是跟著 git 走的，兩台機器各複習幾張卡之後，這個檔案每次都衝突，而且衝突在一個使用者無法用眼睛判斷對錯的格式上。
- **每張卡一個檔，只存目前狀態**（`due`、`interval`、`ease`）：檔案小、讀取快。但歷史被丟掉了——「這張卡我失敗過三次」是使用者真正想知道的事，也是日後想換演算法時唯一的依據。演算法一改，舊狀態就沒有意義，而且無法回推。
- **每張卡一個追加式紀錄檔，狀態由重放算出（採用）**：跨機器合併時不同卡片是不同檔案，天然不衝突；同一張卡在兩台機器上各複習一次會衝突，但衝突內容是兩行人看得懂的日期，解法顯然。歷史完整保留。

## Consequences

- **排程不是儲存的資料，是計算的結果。** 換演算法（例如日後真的要上 FSRS）只要改重放函式，全部歷史照樣適用，不需要任何遷移。這是選追加式紀錄最實際的回報。
- **`build` 絕對不寫 `notes/reviews/`。** build 的定義是「從真實來源重建產物」，而這裡的因果是反的。複習紀錄只有一個寫入者：server 的評分端點。
- **紀錄跟著卡片編號走，不跟著檔名。** 卡片檔名含 slug 且可以改，編號不會；`reanchor.py` 換版本時重寫的是 anchor，從不動 `id`。所以原文重新轉檔、重新切分都不影響複習歷史——這正是 ADR 0001 那套「卡片編號不帶章節前綴」的規定現在的回報。
- **卡片被刪除時，紀錄留著並回報為孤兒。** 靜默刪掉使用者的複習歷史，和靜默跳過一張讀不了的卡是同一種錯。他要清就自己清。
- **必須跑 server，沒有離線評分。** 畫記在沒有 server 時退回 localStorage 是可接受的，因為畫記丟了可以重畫；複習排程丟了無法重建。localStorage 是使用者清一次瀏覽器資料就消失的地方，把不可重生的資料放在那裡是自相矛盾的。沒有 server 時，複習分頁明說功能未啟用，不假裝能用。
- **評分不觸發重建。** 畫記存檔會重建複習頁，因為畫記改變頁面內容；評分不改變頁面內容，只改變排程。一次複習可能評十幾張卡，每張都重建一次 800 KB 的頁面是不可接受的。頁面改成向 server 要目前的排程（`GET /_pa/reviews`），所以永遠是新的。
- 代價是多一個目錄、多一種格式，而且複習排程只在 server 開著時才看得到。這是刻意的：這份資料值得這個代價，其他產物不值得。
