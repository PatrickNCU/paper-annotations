# server 可以改卡片，但只能取代兩行、在檔尾追加，永遠不重新序列化

到 1.16.0 為止，`notes/cards/` 只有兩個寫入者：使用者本人，和替他寫卡的 agent。server 寫 `notes/marks/`（畫記）與 `notes/reviews/`（複習紀錄，ADR 0003），卡片一個位元組都不碰。

1.17.0 的半懂出口打破這一點。半懂的卡在複習區永遠排最前面，但頁面上沒有任何方法把它關掉：他得回到對話裡說「我懂了」，agent 改 `status:`，再重建。「懂了」這個判斷發生在頁面上——他剛用自己的話寫了一遍、剛對過解答——卻要跑到另一個地方才生效，這條動線在試玩時就被否決了。所以 server 需要能做兩件事：把 `status:` 改成 `resolved`、把 `updated:` 改成今天；把他寫的那句話記進卡片的 `## 自己的話`。

問題在於怎麼寫。卡片是使用者手寫的檔案：有他自己加的註解、`|-` 的多行引文、他排的 key 順序。`notes.write_doc` 走 `miniyaml.dump`，會把這些全部正規化掉——在一個他當成自己筆記的檔案上，這是資料損失，只是不會報錯的那種。

我們決定：**server 對卡片的寫入限定為文字層面的兩種操作，絕不經過 YAML 序列化。**

1. 用正規表達式取代 frontmatter 裡的 `status:` 與 `updated:` 兩行（缺哪一行就在 `---` 前補上），其他內容逐位元組不動。
2. 在 `## 自己的話` 段落尾端追加一行 `YYYY-MM-DD 種類：文字`；段落不存在就在檔尾建立。段落上方的內容一個字都不改。

這兩個操作是 `notes.set_card_status` 與 `notes.append_self_line`，是 server 寫卡片的唯一入口。`/_pa/card` 端點只接受 `half` 狀態的卡、只接受 `resolve` 與 `keep` 兩個動作。

## Considered Options

- **不讓 server 寫卡片，半懂出口只複製文字回對話**：架構最乾淨，但動線斷在最要緊的地方。他在頁面上做完全部的思考，結果要換視窗貼字，然後等 agent 改一行 YAML 再重建；做過兩次就不會再做。
- **用 `miniyaml.dump` 重寫 frontmatter**：程式碼最短。但會丟掉他的註解、把 block scalar 折成單行、重排 key。他打開卡片會發現「不是我寫的樣子」，而且說不出是哪裡變了。在使用者親手維護的檔案上，這種靜默改寫比明確報錯更糟。
- **狀態改寫進 `notes/reviews/` 或另一個 sidecar 檔**：卡片不動，但狀態變成兩個真實來源——卡片說 `half`，別的檔說 `resolved`，build 要決定信誰。ADR 0003 選追加式紀錄正是為了不讓排程有第二份真相，這裡不該反過來做。
- **文字取代加檔尾追加（採用）**：程式碼多幾行，換來「他看到的檔案就是他寫的檔案，加上兩行改動」。可以用 `git diff` 一眼核對。

## Consequences

- **agent 也守同一條紀律。** 對話裡改狀態時，同樣只換那兩行、只在 `## 自己的話` 追加。這條規定寫進 SKILL.md 與 `commands/review.md`；`write_doc` 留給整張新建的卡。
- **`## 自己的話` 是使用者的原文。** 工具追加、不改寫；語言規範（繁中句子、術語單一形式）對這一段不適用——那是他說話的樣子，不是我們的。
- **改狀態會重建兩個產物。** 跟評分不同（ADR 0003：評分不重建），狀態在註記檢視、`QUESTIONS.md`、`catalog.json` 裡都看得到，所以 `/_pa/card` 跑完 `build_annotated.py` 與 `build_html.py`，頁面重新載入。一次只關一張卡，成本可接受。
- **只有半懂的卡能從頁面關。** `open` → `half`、`resolved` → `open` 這類改動仍然是編輯檔案；頁面提供的是那一條被驗證過的動線，不是一個通用的狀態編輯器。
- **一句話直覺的作者記在 `intuition: agent | user`。** 他自己寫的一句話取代 agent 寫的之後，頁面顯示「你寫的」，這個欄位是唯一的依據。缺省視為 `agent`。
- 代價是 `notes.py` 裡多兩個帶正規表達式的函式，以及「卡片可能被 server 改動」這件事要讓 `git diff` 看得懂：改動永遠是兩行取代加檔尾追加，別的樣子就是 bug。
