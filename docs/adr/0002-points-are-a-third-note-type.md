# 要點是第三種筆記類型，不是畫記的變體

系統原本只有兩種筆記，而且兩種都由使用者的行為驅動：他卡住才有疑問卡，他標記才有畫記。這代表**系統的視野等於使用者的困惑**——他讀懂的部分不留任何痕跡。跨論文的關係卻恰恰長在他讀懂的地方：兩篇論文會不會矛盾，矛盾的是**主張**，不是疑問。

因此需要第三種筆記，記錄論文的骨架（主張、方法、假設、定義、結果、限制），由 agent 在閱讀時產生。我們決定把它做成獨立的類型 `notes/points/`，而不是在既有的畫記上加一個欄位。

## Considered Options

- **在畫記加 `kind` 欄位**：最省程式，錨點解析與複習頁渲染全部現成。但 `SKILL.md` 對畫記畫了一條刻意的界線——「畫記不需要你判斷或整理：哪一段、什麼顏色、註解寫什麼，都是使用者已經決定好的」。要點恰恰相反，它整個就是 agent 的判斷。同一個檔案類型同時承載「使用者已經決定的」與「AI 推測的」，三個月後分不出誰說的，而分得出來正是這套工具對使用者的核心承諾。
- **寫成 `origin: suggested` 的疑問卡**：不必新增類型，而且「AI 主動標註」已有先例。但卡片的骨架是 `## 問題／## 卡點／## 解答`，要點沒有問題也沒有卡點，硬塞會生出假的疑問，並且污染「疑問 N 則」的統計與複習動線——使用者會看到一堆他從來沒問過的「疑問」。
- **只做論文層級的結構化摘要**（一篇一個檔，不錨到段落）：最便宜，但失去位置。跨論文連結要能說「這篇第三節的做法對應到那篇第六節」，沒有錨點就退化成散文，等於現有的 digest 再做一次。
- **獨立的 `notes/points/`（採用）**：格式與生命週期自成一套，但**共用 `pa/anchors.py` 的解析與複習頁的渲染管線**。新增的是語意，不是基礎建設。

## Consequences

- 真實來源從兩種變三種：`notes/cards/`、`notes/marks/`、`notes/points/`。build 仍然冪等，`annotated/` 與 `index.html` 仍然完全可重生。
- 要點必須記 `origin`。`origin: agent` 的在複習頁上比使用者自己的畫記安靜，並且可一鍵隱藏——沿用 `origin: suggested` 已經建立的規矩。
- 要點不進「疑問 N 則」統計、不進疑問清單，與畫記同一條界線。**它不是待辦，是索引。**
- 錨點規則不變：`ref → heading → quote`，解不到就不掛，不猜。要點沒掛上不影響任何既有功能。
- 新的失敗模式是**信噪比**，不是正確性。要點由 agent 主動產生，量一旦失控，使用者會關掉整個功能而不是修它。因此每回合結尾必須列出新增的要點供當場否決，開卷掃描必須有數量上限，寧可少而準。
- 代價是第三種類型要各自維護格式、匯入匯出與說明文件。這是刻意付的成本，換來的是「哪句是作者的、哪句是使用者的、哪句是 AI 補的」永遠分得清楚。
